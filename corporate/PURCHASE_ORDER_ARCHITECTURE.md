## Architecture decision

Retain React/TanStack Start/Nitro on Amplify and GitHub Actions. Add a separate purchase-order backend, not a spreadsheet transaction ledger:

1. **Identity:** Cognito user pool, authorization-code + PKCE login, verified email, staff MFA, no public staff signup; server validates issuer/audience/signature/expiry/token-use with maintained JWT library. Opaque HttpOnly Secure SameSite=Lax session, rotating server session records. Organization membership, current qualification and revocation checked on every request from DynamoDB, not from browser fields or stale token groups. Roles: sales drafts; approver qualifies/releases/cancels; finance views reconciliation; client accesses only assigned organization/order; integration service receives validated provider facts. Require a separate approver from the draft creator. Marketing cookie cannot authorize orders.
2. **Storage:** DynamoDB orders, approved organizations/memberships, legal-term releases, inbox, audit and outbox. Separate sandbox resources. A TransactWriteItems transaction must conditionally update order.version, put unique provider/event key, append audit event and write effects together. GSIs for authorized organization and staff status queries. Order revision is immutable after release. Use integer CAD/USD minor units, bounded quantities and saleable SKU allowlist; source addresses/tax exemptions must be verified server-side. No client totals.
3. **Evidence:** private S3 with Block Public Access, SSE-KMS, versioning and legal-approved retention; archive exact pre-sign PDF, signed PDF, Adobe audit report and SHA-256 digests. Presigned download after authorization, short expiry, no public document URLs. Audit records append-only for app role; separate retention-controlled archival role. Hash chaining aids detection but is not tamper-proof without IAM and immutable archival.
4. **Workflow:** EOI → staff qualification → draft → second-person approval → review/sign → signature API verification and archive → hosted payment → provider-confirmed paid → receipt. Public EOI never creates an order or reserves stock. Terms counsel must define the binding moment, seller countersignature requirement, signatory authority, cancellation/refund rights, governing law and payment timing. No claim that the simulation creates a binding contract.
5. **Signing:** Adobe OAuth application and entitlement verified manually. Render full frozen order revision, terms version/hash, seller, buyer legal identity/authority, market, SKU quantities, negotiated prices, currency, addresses, final tax/shipping, expiry and total. Server maps Adobe agreement ID to revision digest and signer. Adobe GET intent challenge checks/echoes configured X-AdobeSign-ClientId. This client ID is not a secret or a cryptographic signature. POST is only a hint: durably enqueue then OAuth-fetch the known agreement, participant completion, signed documents and audit report; verify all required signers completed and revision mapping before advancing. Use webhook OAuth protection where entitled; allowlisted IDs and API re-fetch remain mandatory. Ignore browser return URL as evidence.
6. **Payment, preferred:** Shopify Admin draft-order calculation/create from approved mapped variants and negotiated pricing, with verified shipping destination, tax rules and currency. Pin API `2026-10` after contract validation. Acquire a least-privilege server app token: read_products, read_draft_orders/write_draft_orders, read_orders; add read_customers only if needed. Confirm protected customer-data access. Do not assume a write_webhooks scope: subscriptions depend on topic/resource access and app configuration. Build final quote using Shopify totals before signing; block discount codes/checkout edits where supported and contract-test those controls. Recheck final totals after signature before releasing invoiceUrl. If anything changes, invalidate the revision and re-sign, never silently adjust the charge. Keep invoice URL server-side until signing; treat it as a bearer capability that recipients can forward. Strict payer identity may require additional checkout controls or the fallback. Do not call draftOrderComplete to fabricate paid state and do not configure automatic fulfillment from unverified payments.
7. **Stripe fallback:** separate test account/keys; hosted Checkout only, mode=payment, pinned API/official SDK, unique idempotency key per revision, immutable server-calculated amount, currency and PO digest metadata, no user-controlled price IDs/redirect URLs. Cards never touch our server or logs. Payment methods initially immediate card payments; delayed methods need async succeeded/failed handling. Verify raw-body timestamped signature via SDK, then fetch session/payment intent; enforce account, livemode, payment_status, amount/currency, order and session mapping. No payment success from redirect alone. PCI responsibilities still require merchant validation; hosted checkout does not automatically establish compliance.
8. **Reconciliation:** Shopify raw-body HMAC with constant-time comparison, configured shop domain/topic and stable webhook event ID; acknowledge only after durable inbox write. Authenticated Shopify order/transaction re-fetch must confirm draft linkage, successful transaction, gateway, currency, full amount and test flag. Handle duplicate/out-of-order retries, abandoned checkout, payment received after expiry, unmatched/manual payments, partial payments, refunds and disputes through explicit exception states. Run scheduled reconciliation for missed events. Approved cancellations with an active checkout require provider invalidation plus race-safe payment reconciliation; signed obligations cannot be erased by editing an order. Never issue refunds automatically in this phase.
9. **Sync and receipt:** transactional outbox worker with backoff, attempt count, leasing, dead-letter queue and staff retry. Upsert a separate status Sheet by order ID/version; suppress stale events. Sheet contains only order ID/version/status and permitted staff fields, no wholesale prices, signatures, health information or checkout URLs. Escape spreadsheet formula prefixes. Staff mail to info@biosciglobal.net links to authenticated dashboard; authenticated sender (SES verified domain or approved existing bridge), no commercial terms in email. Paid receipt derives from reconciled transaction, includes seller/tax registration fields approved by counsel, order version, amount/currency, transaction reference and signed-document link after login. Retry effects independently; provider mail must support a dedupe strategy because delivery cannot be guaranteed exactly once across a network timeout.

## Planned HTTP surface

All private responses `Cache-Control: private, no-store`, noindex and no-referrer. Bounded streamed bodies, strict schemas, same-origin plus session-bound CSRF tokens on mutations, durable rate limits, no CORS credentials wildcard. Invitation: 256-bit random secret stored hashed, one-use/expiry/revocation, verified recipient account binding; never grant access merely because a token exists. Never log tokens or client documents. Sandbox contact delivery must be disabled, since inherited Apps Script URL could notify real staff.

| Endpoint | Access and operation |
|---|---|
| POST /api/lead | Public, existing nonbinding EOI only |
| GET /internal/orders | Staff/client authenticated dashboard with role-scoped server queries |
| GET/POST /api/purchase-orders | Staff list/create; client assigned read only |
| POST /api/purchase-orders/:id/revisions | Sales, expected version, draft only |
| POST /api/purchase-orders/:id/release | Separate approver, current qualification and approved legal release |
| POST /api/purchase-orders/:id/signing-session | Assigned verified signer, fresh Adobe signing session |
| POST /api/purchase-orders/:id/checkout | Assigned client, verified signed revision; service creates hosted session |
| GET/POST /api/webhooks/adobe | Intent challenge / durable hint then authenticated re-fetch |
| POST /api/webhooks/shopify or /stripe | Provider-specific verification and durable inbox |
| GET /api/purchase-orders/:id/receipt | Assigned client or authorized staff, confirmed payment |

These endpoints are a design contract. Only the top-level disabled purchase-orders endpoint and activation page are wired in this foundation. There is no hidden env switch to enable signing or payment.

## Implemented safe scope and limits

- Typed server domain: validated snapshots, SHA-256 frozen revision, separate approver, qualified/legal hash gates, private read policy, verified-evidence transitions, test-only checkout/payment, matching amount/currency/provider/reference, version conflict and idempotency conflict handling, audit chain and outbox intent.
- SimulationRepository is strictly test-only in-memory storage. It is not durable authorization, provider verification, delivery, evidence storage or a production database. Actor and evidence inputs must come from trusted adapters, never JSON request fields. No configured provider adapter exists.
- Shopify HMAC helper and Adobe challenge helper have tests but no public webhook endpoint. Adobe completion requires the proposed API re-fetch; challenge echo alone must never advance state.
- Public nonbinding copy; `/api/purchase-orders` returns 503; `/internal/orders` has no client data, prices, signing or payment controls. Live capture is absent by construction.
- Unit tests use TEST-ONLY SKU and synthetic identities. They verify guards, cloning, duplicate/stale mutations, reconciliation and no commercial detail in Sheet projection. No real signature, charge, mail, Sheet write or Shopify mutation.

## Credentials and manual activation checklist

Provide values only in approved secret settings, never chat/GitHub/browser. Runtime uses scoped Secrets Manager references, not build-time injected values. Adobe: client ID, client secret, refresh token, account/base URI from approved OAuth discovery, webhook ID and optional webhook OAuth credentials. Shopify: separate development store first, app installation/token and webhook secret, approved variant mapping and API version. Stripe fallback: test secret key/webhook secret and merchant account ID. Google: service account limited to the dedicated status Sheet, or a separately versioned authenticated Apps Script bridge; separate sandbox destination. AWS: Cognito pool/client, DynamoDB tables/indexes, S3/KMS, worker permissions, SES verified sender and sandbox recipients. No shared production compute role.

Merchant must resolve **BIOSCIENCE USA INC versus Bioclean Innovations Inc.** with Shopify/processor; confirm contracting/settlement entity, country, business registration, beneficial owners/representative identity, supported bank account, product eligibility, tax registrations, refund policy, statement descriptor and KYC approval. Do not change legal account details or toggle live-store test mode in this task. Adobe API entitlement/OAuth approval and sender licensing must be activated by account administrator. Terms, signer authority, jurisdictions, privacy notice/DPA, consent, retention/deletion versus legal holds and data residency need counsel signoff.

Before real activation: durable auth/storage/adapters and dashboard implementation, vendor contract tests on dedicated test accounts, proof of signature/PDF/audit digest mapping, tampered/replayed webhook and cross-tenant tests, crash/retry transaction tests, duplicate checkout/receipt tests, mismatch/refund/dispute/late payment tests, Sheets/email outage recovery, access revocation and rollback verification. Then obtain explicit authorization for live capture. This draft PR is not a live activation request.
